# 学校变革陪跑工作台

## PRD v1.5 — Methodology-Grounded Assessment Freeze

**状态：产品冻结基线**  
**产品性质：非商业 / 单用户 / Local-first / Consultant Dev Tool**  
**唯一主要用户：学校变革陪跑顾问**

---

# 0. 产品最高原则

本产品的第一设计原则不是功能完整，而是：

> **想尽一切办法降低学习和使用门槛。**

正式产品设计原则：

> **顾问负责工作，系统负责记账。**

顾问日常只应该感知三件事：

> **说情况 → 做判断 → 看变化。**

后台可以存在：

- Stage；
- StageTarget；
- Evidence；
- Diagnosis；
- Snapshot；
- AgentRun；
- ACP；
- MCP；
- DSH；
- Codex；
- SQLite；

但这些复杂性原则上不进入顾问的认知负担。

---

# 1. 产品定义

学校变革陪跑工作台是：

> **一个帮助顾问持续看清“学校现在怎么样、为什么、发生了什么变化、下一步应该看什么”的本地工作空间。**

产品形态正式冻结为：

> **安装在顾问电脑上的桌面客户端。**

界面采用 Web UI 技术实现，但用户不通过浏览器访问，也不依赖远程 Web 服务。

顾问可以直接：

- 说一句情况；
- 拖入一个文件；
- 粘贴一个飞书链接；
- 要求系统查看某次会议；
- 提供一次现场观察。

Agent 自动：

- 查看学校历史；
- 获取当前阶段；
- 理解阶段目标；
- 查找飞书材料；
- 阅读文件；
- 提取事实；
- 对照已有判断；
- 找支持证据；
- 找相反证据；
- 发现变化；
- 提出新的判断。

Agent 的判断必须同时受以下方法约束：

- 五维全等框架；
- 当前阶段目标；
- 校长 / 中层 / 教师行为成熟度标准；
- Schooling by Design 的逆向设计逻辑；
- Data Wise 的证据探究与实践反思逻辑。

两书的正式使用边界、交叉映射和 Agent 判断规则，分别沉淀在 `knowledge/methodology/` 下的 Pack、Crosswalk 与 Assessment Protocol 中。书籍方法论只提供检查问题、证据要求和推论护栏，不形成独立总分。

顾问只负责最终专业判断。

# 3. 产品核心闭环

```text
真实学校工作持续发生
        ↓
顾问告诉系统发生了什么
或让 Agent 自己去查看材料
        ↓
Agent 阅读当前学校状态
        ↓
Agent 阅读当前阶段目标
        ↓
Agent 获取相关真实材料
        ↓
提取事实
        ↓
比较历史
        ↓
发现变化 / 冲突 / 问题
        ↓
提出新的判断
        ↓
顾问：
认同 / 修改 / 不认同
        ↓
形成正式判断
        ↓
系统提示学校状态是否需要更新
        ↓
顾问确认
        ↓
形成新的学校状态记录
```

## 3.1 双循环专业模型

学校状态使用外循环：

```text
阶段期望结果
↓
可接受的达成证据
↓
当前组织现实
↓
目标与现实的差距
↓
干预与下一轮观察
↓
状态变化
```

教师实践使用内循环：

```text
学习证据
↓
教师 / 团队当前实践
↓
可行动的实践问题
↓
尝试新的行动
↓
评估对学习的影响
```

两种循环都不自动产生正式结论。Agent 形成候选判断，顾问完成最终裁定。

## 3.2 学校状态的正式判断基础

```text
学校当前状态
=
五维结构
+ 当前阶段目标
+ 当前团队特征
+ 角色行为锚点
+ 支持与相反证据
+ 顾问专业判断
```

书籍和标准提供判断方法，不提供自动分数。

# 4. 顾问只做三种动作

## 4.1 说情况

例如：

> 看看昨天的中层会议。

> 这是今天现场听课的录音。

> 校长说中层已经能够自己拆任务了，你帮我看看实际材料是不是这样。

顾问不需要先指定：

- Evidence 类型；
- StageTarget；
- Dimension；
- Framework；
- Diagnosis Type。

---

## 4.2 做判断

系统提出：

> 我发现一个新的情况，想让你确认。

顾问只需要：

```text
认同
我想改一下
不认同
```

---

## 4.3 看变化

学校状态页面优先回答：

> 现在怎么样？

> 和上一次相比哪里发生了变化？

> 为什么这样判断？

> 哪些事情目前还不能确定？

# 5. UX 硬约束

## 5.1 数据模型不能直接变成菜单

内部存在：

```text
Stage
Evidence
Diagnosis
Snapshot
AgentRun
```

不等于 UI 需要：

```text
阶段管理
证据中心
诊断中心
Snapshot 管理
Agent Run 管理
```

---

## 5.2 能自动推断的不填写

Agent 能判断的内容：

> Agent 先提议，顾问确认。

不能要求顾问从零填写。

---

## 5.3 能自动登记的不维护

顾问永远不点击：

> 注册证据。

Agent 自动完成。

---

## 5.4 能自然语言完成的不优先做表单

例如修改 AI 判断：

顾问直接说：

> 不是中层不会做，是校长没有真正放权。

系统重新整理。

---

## 5.5 结论优先，细节按需展开

所有专业页面遵循：

```text
结论
↓
简单解释
↓
依据
↓
相反依据
↓
理论 / 技术细节
```

---

## 5.6 技术概念默认隐藏

默认 UI 不出现：

- ACP；
- MCP；
- Runtime；
- Session；
- codex-acp；
- DSH Profile；
- Device Code；
- OAuth Scope。

## 5.7 判断过程必须可审核

系统必须区分：

```text
观察事实
解释
专业判断
```

每个重要判断必须：

- 能定位到原始依据；
- 主动寻找相反依据；
- 提供合理的替代解释；
- 说明目前还不能确定什么；
- 在证据不足时选择暂不判断。

不向顾问展示模型隐藏思维过程，只展示可验证的依据与简明解释。

> 不要求用户理解超过 3 个系统概念。

## 28.1 下一轮观察与行动

状态确认后，系统可以自然呈现：

```text
下一轮值得重点观察

• 中层能否在没有校长代替决策时独立拆解任务
• 教研组是否开始引用学生学习证据

可以尝试

• 由中层独立主持一次任务拆解会议

如何判断是否有效

• 中层形成明确分工、决策依据和后续验证方式
```

这不是待办系统。Workbench 不追踪任务完成率，只记录与下一轮专业判断有关的行动和影响证据。

# 29. 教师实践

保留一级导航。

顾问可以直接：

> 看一下张老师这节课。

然后提供：

- 教案；
- 课堂录音；
- 教师反思；
- 教研组讨论。

Agent 自动识别：

```text
教案本来想怎么教
课堂实际怎么教
老师自己怎么看
教研组怎么看
```

同时必须识别：

```text
学生实际表现出了什么
哪些是观察事实
教师实践与学习结果可能有什么关系
还有哪些替代解释
```

---

# 30. 教师实践默认回答

优先回答：

> 这节课最大的差距是什么？

> 老师自己已经看见了什么？

> 老师还没有看见什么？

> 教研团队真正关注的是什么？

> 当前最值得共同解决的实践问题是什么？

> 下一步可以尝试什么？

> 用什么学习证据判断行动是否有效？

不先展示复杂指标。

实践问题必须：

- 基于学习证据和成人实践证据；
- 在教师或团队可影响的范围内；
- 足够具体，可以采取行动；
- 同时描述已有优势和下一层需要发展的实践；
- 不把对学生或教师的推断冒充事实。

---

# 32. 飞书授权必须由 Workbench 接管

虽然业务读取由 Agent → `lark-cli` 完成，但：

> **任何需要人参与的授权交互，必须由 Workbench Experience Layer 接管。**

不能让 Agent 对顾问说：

> 请复制以下 URL……

不能要求用户：

- 开终端；
- 输入命令；
- 复制 Device Code；
- 回来回复“授权好了”。

---

# 33. 飞书授权核心 UX

正式冻结为：

> **Browser First + QR Always Available + Auto Resume**

中文：

> **默认浏览器优先、二维码始终可用、完成后自动继续。**

---

# 34. 为什么默认浏览器优先

用户大概率已经在默认浏览器登录了飞书。

因此授权时 Workbench：

> 自动使用系统默认浏览器打开官方授权页面。

不使用 Electron 内嵌浏览器。

避免：

> 用户再次登录飞书。

---

# 35. 飞书授权 UI

需要授权时，Workbench 自动打开默认浏览器，同时显示：

```text
需要确认一下飞书权限

已经在你的默认浏览器中打开授权页面。

完成授权后，这里会自动继续。


       ┌─────────────┐
       │             │
       │   QR CODE   │
       │             │
       └─────────────┘

也可以直接用手机扫码授权。


● 等待授权……

[再次打开浏览器]
```

---

# 36. 二维码不是另一个授权体系

二维码由：

> 飞书官方 verification URL

本地生成。

二维码只是把同一个官方授权地址转换为手机扫码入口。

不重新实现 OAuth。

---

# 37. 浏览器和二维码不是让用户做选择题

Workbench 不先问：

> 浏览器授权还是扫码授权？

系统直接：

1. 自动打开默认浏览器；
2. 同时显示二维码。

用户自然选择最方便的方式。

# 51. V0.1 UX 验收

必须做到：

- 新建学校只有一个字段；
- 不要求先创建阶段；
- 不要求配置 Baseline；
- 不要求注册证据；
- 一句话可以开始分析；
- 日常不显示 Agent Runtime；
- 飞书授权不复制 URL；
- 飞书授权不输入 Device Code；
- 飞书优先打开默认浏览器；
- 同时提供扫码；
- 授权后自动恢复任务；
- 状态 Commit 不暴露 Snapshot 概念；
- 事实、解释和判断明确分离；
- 每个关键判断显示支持与相反依据；
- 证据不足时允许暂不判断；
- 教师实践从学习证据进入成人实践；
- 建议行动同时说明如何验证影响；
- 方法论、书籍检索和 RAG 不进入日常 UI；
- 技术错误默认翻译成人话。

# 52. 最终产品原则

> **顾问负责工作，系统负责记账。**

> **说情况、做判断、看变化。**

> **能推断的不填写。**

> **能自动记录的不维护。**

> **能直接完成的不让用户选择。**

> **复杂信息按需展开。**

> **授权只在真正需要时出现。**

> **学校状态属于 Workbench。**

> **专业推理属于 Agent。**

> **方法论约束推理，证据约束判断。**

> **最终判断属于顾问。**
