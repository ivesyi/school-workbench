### 更正一：路线图是存在的，在 SPEC 里

`docs/architecture/SPEC.md` 第 67–69.1 章定义了**四个纵切**。而且实际建造顺序与它**不一致**：

- SPEC 第一纵切 = 全链路真货（说一句话 → 飞书授权 → Agent 用 lark-cli 读会议纪要 → MCP 登记证据 → MCP 提交判断 → 顾问确认），同时验证 ACP / MCP / DSH-Codex / lark-cli / 授权 / Evidence / Diagnosis / Human Review
- 实际建造：把第二纵切（起点状态）、第三纵切（状态变化）用**确定性引擎**先做了，把第一纵切最难的那截（真 AI + 飞书 + MCP 写面）推后

**当前处境 = SPEC 第一纵切尚未开始。**

### 更正二：`pack.json` 没有漏搬内容，任务书把缺陷说重了

## 4. 当前唯一卡点

> **用户需要亲自在审核工作台里逐条看那 10 条准则，判断它们是否足以约束真实判断。**

这是**只有用户能做的判断** —— 激活的语义就是「顾问正式承认这份方法论可以约束真实判断」，不能由 Claude 或 worker 代做，也不该由代码自动完成。

操作路径：

```bash
pnpm dev
# → 设置 → 高级设置 → 方法论内容审核
```

两种结局：

- **够** → 逐条签署 → `pnpm methodology:activate --pack <key> --version <ver> --apply` → 提交 → 接 AI 那一轮立刻可开工
- **不够** → 用户指出是哪几条、缺什么 → 那时才需要找回原书，且要**升版本**（见下）

### 若要改 Pack 内容，必须升版本

`packages/db/src/sqlite-methodology-repository.ts:166` —— 同 key + version 但内容不同时 `syncRegistry` 直接拒绝（`already exists with different content`）。所以任何内容修改都必须 `schooling-by-design v1 → v2`、`data-wise v3 → v4`，且 `PACK.md` 的版本头要同步。当前没有任何已提交判断引用 Pack 版本（方法论从未上线），升版本是干净的。

## 5. 为什么必须先过方法论这道门槛（代码级证据）

不是流程洁癖，是架构故意砌的墙。已在代码中核实：

- `packages/assessment/src/context.ts:325` —— Pack 不是 `active` 直接报错 `Methodology pack <key>@<ver> is not active.`
- `packages/assessment/src/validator.ts` —— `resolvedMethodology.length === 0` 且候选 `status === 'proposed'` 时报 `ASSESSMENT_ABSTENTION_REQUIRED`，候选**必须弃权**
- `SPEC` 第 75 章（冻结）明令禁止「无 Criterion 引用地形成正式 Diagnosis」
- `SPEC` 第 24 章 —— 只有过 `validateAssessmentCandidate` 的候选才能映射为 `DiagnosisProposal` 进入 HumanReview，不得用第二套宽松 DTO 绕过

**后果：Pack 不激活就接真 AI，AI 能读材料、能提取事实，但每一条判断都只能输出「证据不足，暂不判断」。** 那不是真实运行形态。

用户已明确拒绝「绕过 assessment 契约走 legacy 通路」这条捷径。

## 6. 接 AI 那一轮的已知地基（本会话核实部分）

架构约束（`SPEC` 第 7、8 章，冻结）：

- Agent Host **只负责 ACP**（runtime discovery → spawn → initialize → capability negotiation → session → prompt → status → permission → cancel → teardown），不放任何学校业务逻辑
- 进 V1 的 runtime 必须「可通过 ACP 驱动 **且** 支持 MCP」，首批 = DeepSeek Harness、Codex，明文写死「不存在不支持 MCP 的兼容模式」
- MCP **不暴露** `diagnosis_accept` / `diagnosis_reject` / `state_commit` / `stage_activate`（第 25 章）
- `diagnosis_propose` 必须结构化提交，不能从回复文本解析（第 23 章）

仓库现状：

- `packages/workbench-read-plane`（7 个只读 tool + 能力令牌 + loopback）与 `packages/workbench-mcp`（stdio）已建好，但 **Electron 启动时没有启动 loopback server**
- **MCP 写面（`evidence_register` / `diagnosis_propose`）完全没做**
- **Agent Host 完全没做**
- PRD 第 15 章要求「设置里选默认 AI 助手」、第 16 章要求只显示高层进度（不显示 Shell / Tool JSON / Token / 思维链 / ACP Event / Session ID）—— **都没做**

## 8. 工作方式约定（本会话沿用，建议保持）

- 主会话只当 orchestrator：拆解 / 派发 / 验收 / 汇报，不亲自写实现代码
- 执行 worker 默认 Agent tool + 显式 `model: "opus"`
- 派工前把简报写进 scratchpad 文件，简报必须自包含：背景、已锁定决策、必须交付、明确不做、不可破坏的不变式、纪律条款、验收命令、答卷格式
- 纪律条款必写：「实现与预期不符时不许硬凑，停下报告」「台账里不写没验证过的数字」「不许写会让 git 判为二进制的文件」
- **验收在主会话**：独立复跑全部验收命令、审 diff 范围与关键 hunk、检查二进制文件、抽验关键事实断言。worker 自报数字不复跑不采信
- 本地 commit，**不 push**，由用户验收后决定

本会话两次抽验都有收获：worker 抓到任务书前提失实（主会话复算证实 worker 对）；主会话复比 `PACK.md` 与 `pack.json` 后推翻了任务书对翻译质量的定性。**任务书的前提要当假设查，不要当事实用。**
